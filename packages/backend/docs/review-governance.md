# Review governance

Review governance is opt-in. Start in **shadow** mode with a small manually entered policy and a labeled benchmark; move to **enforced** only after reviewing the pilot evidence. Enabled projects require review on every task. The Governance tab in Project Settings contains configuration, the human docket, approved releases, proposals, and decision history.

## Owner setup

Set `OPENSPRINT_GOVERNANCE_OWNER` to the designated reviewer's name and `OPENSPRINT_GOVERNANCE_APPROVAL_SECRET` to a separate random secret of at least 32 characters on the backend. Enter this capability in the Governance tab when making an authorized decision. The browser keeps it in component memory; it is not the ordinary local bearer token. Task subprocess environments remove these values. Never put the capability in a task, policy text, prompt, tracked file, or project setting.

The local owner workflow is cooperative. Processes with unrestricted access under the same OS identity can inspect server files, memory, or environments. For shared installations, run the backend under a separate OS account and give each authorized reviewer an appropriate protected access path. The capability does not claim to provide a tamper-proof boundary against the machine owner.

Choose the database before configuring governance authority. Live database URL replacement and migration are blocked while server approval authority or retained approved policy exists, because replacing the database could discard holds. Database maintenance must stop the server and preserve all governance, replay-input, and lease tables; SQLite/PostgreSQL migration coverage verifies their dependency order and session IDs. Never point a governed server at an empty database to release a hold.

An unreachable database does not disable governance, even if approval credentials are missing after a restart. Restore access to the original database before publishing or changing protected settings; restore the owner's credentials before recording new decisions.

Create standards with stable rule and revision IDs, full text and rationale, owner, path/role/component applicability, examples, parent/override relationships, and exception classification. Constraints are non-waivable. Review and activate the initial immutable release, then configure shadow/enforced mode and a separate tool-free API judge. Existing instruction prose is captured as release content; human confirmation is required for imported rules. Future assignments use the approved release; editing an instruction file in a task does not change its authority.

Configure **Read-only reviewer reconsideration** separately from **Judge** in rollout settings. Each has its own API provider/model and human-approved input/output price ceilings per million tokens (`reconsiderationAgent` / `reconsiderationTokenPricing`, `judgeAgent` / `judgeTokenPricing`). Both support Claude or OpenAI APIs without repository tools. A CLI initial reviewer can submit its ordinary findings, then a configured read-only API reviewer reconsiders the appeal before the separate judge. The reconsideration model takes precedence over the initial reviewer. Without an explicit reconsideration model, compatibility reuse is limited to an initial API reviewer matching the judge's provider, model, and endpoint exactly; only then may it use that judge's price ceilings. Missing models or ceilings send an actionable request to the human docket. Clearing either model and its ceilings removes that optional configuration; clearing the judge routes disputed standards to the human docket. All calls reserve the same durable task-wide token, cost, and elapsed-time budgets before invoking either model.

## Dockets and durable holds

Standards findings cite rule revisions and concrete code evidence. Defects need no preexisting standard. Appeals include the requested exception, alternatives analyzed, evidence, risks, and limits. Reviewer reconsideration and judge calls have persistent task-wide budgets. Routine approvals and straightforward fixes do not need a judge.

The docket exposes require-fix, one-time allowance, reusable allowance with explicit path/rule/expiry predicates, request-evidence, cancellation, and abandonment. A stale or human-cancelled case can only require a fix, stay cancelled, or be abandoned: requesting evidence would return it to a state where an allowance is reachable. Abandoning closes the task without merging once no other case holds it. A one-time allowance survives re-review of the same code, release and diff when the new finding names the same category, rule revision and file, whatever its wording; valid rulings are given to the resumed reviewer. Reusable allowances apply only to cases under the same release and never once that release is critically revoked. Each decision records the named actor and rationale, code and policy binding, finding IDs, and immutable evidence. One-time allowances remain discoverable but do not authorize future exceptions. Revocation preserves the historical event while preventing future reuse and invalidating pending approval. Revoking a decision is idempotent, leaves alone a case that a later ruling has already decided, blocks and unassigns the affected task, and pauses its running agent.

Waiting cases retain the worktree, release agent slots, and survive restart. Recovery escalates an adjudication only when its claim came from an earlier server process; the watchdog leaves this process's own model calls alone. A model result that arrives after a human or recovery moved the case is discarded. A reviewer rejection without structured findings becomes a fix request carrying the reviewer's issues, and defects in files the change did not edit are recorded. Normal task reopening, notification deletion/resolution, and autonomy changes cannot clear a hold. Human allowances do not waive another angle's blocker, failing hard checks, or protected-path scope. Changed code requires renewed review. The final serialized candidate admission checks the durable state rather than trusting a notification's status.

Archiving or deleting a governed project requires the separate owner capability and completed governed work, with no outstanding docket or remote publication. The home-screen confirmation requests this capability only when needed and retains it in memory. Historical policy evidence stays retained independently of ordinary project cleanup.

Task scope is captured atomically when a task is created. In enforced mode that wording is evidence only: protected integration, OAuth or token paths need an owner grant from **Standards → Authorize protected scope for a task**, made before the task is assigned. A grant is a list of exact scope values (`integration`, `oauth`, …); prose containing those words grants nothing. In other modes task wording still unlocks protected paths, matched on whole words. A remote review inherits only its original tasks' grants. Changes to policy sources, checker scripts/configuration, or authority code require a separate exact-code human approval in Standards. Checker files include whatever the configured gate commands run, followed through root package scripts, not only conventionally named ones. Symlinked policy or checker files are refused rather than skipped. Basename matches such as `governance*.ts` and `policy-context.ts` apply only to the Open Sprint repository itself. Dependency-only package changes do not require this approval.

When a task's approved source change merges, its new hashes join the approved snapshot, so the merge does not register as drift. Drift in Open Sprint's own runtime and default instructions is audited, not blocking. Other drift holds new enforced assignments until the owner reconciles it: **POST `/releases/reconcile-source-snapshot`** with `expectedActiveReleaseId` and `rationale` re-approves the current sources under unchanged rules and instructions, without replay, and covers work already pinned to the reconciled release. Rollback to an approved, unrevoked release proceeds under the owner capability and records any drift in its event; reconcile afterwards.

Shadow mode is observational. Drift, a missing source approval, and an unstructured rejection are recorded as audit events, and the task falls back to ordinary review. Shadow cases appear in the docket as history but never hold a task; the human docket is for enforced mode.

Activation and rollback are refused while work pinned to another release is unpublished: a running or open task, or a closed task whose remote publication is pending. Blocked tasks can be revalidated and do not prevent activation. Turning enforcement on reaches tasks already pinned in shadow mode, and enforced publication refuses tasks with no pin.

Once retained work exists, review, enforcement, gate and instruction settings change only with the owner capability, and each change is audited. A project that is disabled with no pinned work, open docket, or pending publication treats those settings as ordinary. A governed project's repository path cannot move while it has an active release or retained work.

Governed projects publish SPEC changes through an explicitly scoped Execute task with normal review and hard checks. Approval in the standalone specification-publication workflow cannot substitute for that authority.

Publication receipts preserve the reviewed files and their original scope before the local merge. A remote rebase may carry that approval forward only when trusted code verifies the files and authority remain valid. Conflict resolution or other changed code creates a retained review task against the actual remote base, with the original scope for each file. The task starts with independent review and hard checks; any subsequent fix must be reviewed again. A failed or waiting remote publication cannot trigger automatic deployment. Cancellation, expiry, and critical revocation also block closed local tasks whose remote publication is still pending.

Manual and automatic delivery share the publication lease and require a clean, verified deployable revision before external commands run. Deployment-command and environment settings require the owner capability in governed projects. Repository commands, checks, installers, and delivery subprocesses strip governance capabilities even when command-specific environment overrides try to restore them.

Adjudication calls receive a bounded case (findings, appeals, applicable rules and a diff capped to the budget), not the stored evidence. Reservations are settled against provider-reported usage, so three appeals fit the default budget. The docket summary omits evidence; the selected case's evidence is loaded on demand from `/cases/:caseId`.

Critical policy revocation invalidates pending approvals, pauses affected agents/tasks, and preserves evidence. Activate a compatible evaluated replacement release, then request a fresh policy review from the stale docket. This explicit action preserves the original scope and spent budgets and grants no code approval. Already published commits remain unchanged and receive an explicit remediation marker. Ordinary release activation affects new assignments; critical revocation is a separate administrative action.

## Congress and amendments

Decision mining has its own durable cursor and runs independently of code-audit change detection. Recurrence nominates a rule for review; it does not justify changing it. Each rule revision has one nomination per release: later evidence updates it in place, and it is not redrafted while a draft is open or after rejection. A draft may change only its nominated rule and must cite each piece of evidence on its nominated side. A configured API auditor can draft exact substantive standard text from supporting and contrary decisions. Draft claims are durable and bounded; failed drafts stay available for manual follow-up. The UI also permits manually authored exact proposals. None of these paths activates a rule.

The cursor also processes retained fixes, reconsidered findings, verified dispositions, and reviewer false positives. Such events are labeled advisory evidence, separately from human rulings; they never acquire reusable authority. Distinct cases count toward recurrence, and exact processed-event receipts prevent late or same-time events from being skipped. Draft jobs have expiring claims, at most three attempts, and backoff; failed nominations do not starve later work.

Proposals show complete before/after content, supporting and contrary rulings, positive/negative examples, scope, compatibility, and a required landed enforcement commit. Evaluation binds the candidate content hash. Amending a rule gives each rule that links to it a new revision pointing at the replacement. Human activation uses optimistic concurrency against both the proposal and current release. Rollback restores a previously approved immutable release only with compatible enforcement. Unlanded or incompatible enforcement requires a normal scoped implementation task; unrelated Git commits are never reverted automatically.

## Offline replay executor

The old synthetic baseline/candidate outcomes are removed. Production replay uses a server-owned `OPENSPRINT_REPLAY_IMAGE` value pinned to an immutable Docker image digest, for example `registry.example/replay@sha256:<64 hex characters>`. There is no network pull: provision the image and its offline model/toolchain before evaluation. Missing Docker, image, original prompt/commit/fixture, unsupported dependencies, or an incomplete evaluator output produces **incomplete evaluation**, never successful evidence.

Docker is resolved from trusted absolute installation locations rather than the task's `PATH`. A custom installation can use the server-owned absolute `OPENSPRINT_REPLAY_DOCKER` path. A bounded archive reader validates every path before extracting; reserved Git metadata, duplicate/case-conflicting paths, links, and special files are unsupported. Fresh local Git state supports agent commits without exposing host remotes, credentials, hooks, or configuration.

The image must contain two executables:

1. `/opensprint-replay/agent /replay-input/task.json` invokes an actual offline coding agent against `/workspace`. The input contains the original decomposed task input, full selected baseline/candidate instructions, and toolchain identity. Honor `executionContract`, `contextDirectory`, and `resultPath`: resolve `context/` references under the supplied directory and write only the relocated result path. The original absolute worktree prefix is mapped to `/workspace`; local commits are permitted, merging/publishing and external effects are unavailable. Emit one JSON object on stdout: `{ "completed": true, "retryCount": 0, "costUsd": 0 }`. `retryCount` and `costUsd` are image-reported: they are recorded under `imageReported*` metrics and never act as guardrails. Send logs to stderr.
2. `/opensprint-replay/evaluate /replay-evaluation/rubric.json` runs a fixed independent evaluator and every named deterministic check. Emit `{ "rubricId": "...", "label": "compliant", "reviewPassed": true, "checks": [{ "name": "unit", "passed": true }] }`. The evaluator and rubric must not be supplied or modified by the candidate. The rubric omits the fixture's human label, so report what was observed: the five labels are `compliant`, `exception`, `defect`, `conflict`, and `retrieval_miss`. The image must also provide a `timeout` command (coreutils or BusyBox); both executables run under it so a limit applies inside the container.

The server exports tracked source from the retained original base commit into disposable directories. Untracked environment files, live task stores, Git credentials, connectors, and server capabilities are never mounted. Potentially sensitive tracked inputs are rejected. Containers use no network, a read-only image root, an unprivileged UID, dropped capabilities, no-new-privileges, resource/time limits, and a bounded temporary filesystem. Only the workspace is writable for the coder. The evaluator runs in a fresh container with a read-only candidate workspace and receives a rubric unavailable to the coder. Container names permit forced cleanup after client timeout, and a workspace disk watchdog stops a coder that exceeds its budget. Replay containers are labeled; server startup removes any that outlived their time limit and does nothing when Docker is missing. The model and required dependencies must already be in the image; downloading them during replay is unsupported.

Backends running as root assign the validated replay inputs to UID/GID 65534 before launching either container. Completed coder output is untrusted: links, special files, and oversized artifact trees make evaluation incomplete before host cleanup or diffing. If the Docker connection fails and forced container termination cannot be confirmed, its private temporary directory stays quarantined. Stop the corresponding `opensprint-replay-*` container before removing that directory.

**Known limitation: the check and evaluator trust domain.** The evaluator runs in a fresh container, but its rubric checks run against the coder's workspace. Code the coder wrote can execute beside the verdict and influence it, so a rubric check result is not independent of the replayed code. Treat replay as strong regression evidence against a cooperative agent, not as proof against an adversarial one. Separating the two needs a changed replay protocol.

Use the advanced replay section to label a retained completed task session. Before ordinary session pruning, the server retains the exact attempt/invocation, original policy pin, decomposed/full prompts, binary context/specification/plan/dependency artifacts, and original base/head/diff. Routine approvals can supply compliant examples without an appeal. Missing or ambiguous provenance, linked context, or retention-budget overflow makes replay unavailable. Rubrics, labels, and holdout flags are human-authored immutable inputs. Fixtures and full outcome artifacts, including binary code diffs, live under `~/.opensprint/governance-replay/`, outside ordinary session pruning; original inputs also have independent database records and Git retention refs. Treat this evidence as private project data and back it up with the policy database. Never invent missing original inputs. Candidate policy replaces the original policy projection while requirement/dependency evidence stays pinned.

Evaluation requires at least ten fixtures, all five categories, and held-out positive and negative examples. Positive fixtures (`compliant`, `exception`) succeed when the output is accepted. Negative fixtures (`defect`, `conflict`, `retrieval_miss`) succeed when the violation is blocked or avoided; an accepted violation fails. Trusted server code applies this polarity after the blind evaluator reports. Every candidate fixture must succeed: an aggregate tie cannot hide a known missed violation. At least one held-out positive and one held-out negative, from different tasks, must select the amended rule and show policy content that differs beyond release and revision identifiers, so a no-op amendment cannot pass. Tasks cited by the amendment's own evidence never count as held out, and per-fixture coverage is recorded in the evaluation. Measured task success, review outcomes and server-timed latency are compared against baseline; regressions prevent activation. Replays give the coder only the paths in its original policy receipt, without hindsight about what it later changed.

Fixture hashes are bound in the policy database at capture and in the evaluation record. Activation re-reads the artifact and fixtures and refuses any missing or changed evidence. The capability-protected `DELETE /replay/evidence` with `{ "confirm": true }` purges a project's fixtures and evaluations, after which evaluated proposals relying on them must be re-evaluated. This minimum is an activation prerequisite, not evidence of broad improvement. Start with a human-measured baseline and sample routine approvals to detect violations that never escalated. Track human minutes, queue age, reversals, retrieval coverage, escaped regressions, and total cost/latency. Insufficient or conflicting evidence keeps rollout in shadow mode.

Completed sessions with non-failed live user guidance are unavailable as replay fixtures until the full model-turn protocol is supported. Their case evidence retains the exact guidance journal; replay never presents the original prompt alone as the complete input to a guided run.

API entry points are under `/api/v1/projects/:projectId/governance`. The `/replay/sources` and `/replay/fixtures` reads show available retained inputs; capability-protected fixture labeling and `/replay/proposals/:proposalId/evaluate` run the evaluator. No HTTP endpoint accepts arbitrary evaluation scores.
