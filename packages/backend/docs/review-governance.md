# Review governance

Review governance is opt-in. Start in **shadow** mode with a small manually entered policy and a labeled benchmark; move to **enforced** only after reviewing the pilot evidence. Enabled projects require review on every task. The Governance tab in Project Settings contains configuration, the human docket, approved releases, proposals, and decision history.

## Owner setup

Set `OPENSPRINT_GOVERNANCE_OWNER` to the designated reviewer's name and `OPENSPRINT_GOVERNANCE_APPROVAL_SECRET` to a separate random secret of at least 32 characters on the backend. Enter this capability in the Governance tab when making an authorized decision. The browser keeps it in component memory; it is not the ordinary local bearer token. Task subprocess environments remove these values. Never put the capability in a task, policy text, prompt, tracked file, or project setting.

The local owner workflow is cooperative. Processes with unrestricted access under the same OS identity can inspect server files, memory, or environments. For shared installations, run the backend under a separate OS account and give each authorized reviewer an appropriate protected access path. The capability does not claim to provide a tamper-proof boundary against the machine owner.

Choose the database before configuring governance authority. Live database URL replacement and migration are blocked while server approval authority or retained approved policy exists, because replacing the database could discard holds. Database maintenance must stop the server and preserve all governance, replay-input, and lease tables; SQLite/PostgreSQL migration coverage verifies their dependency order and session IDs. Never point a governed server at an empty database to release a hold.

Create standards with stable rule and revision IDs, full text and rationale, owner, path/role/component applicability, examples, parent/override relationships, and exception classification. Constraints are non-waivable. Review and activate the initial immutable release, then configure shadow/enforced mode and a separate tool-free API judge. Existing instruction prose is captured as release content; human confirmation is required for imported rules. Future assignments use the approved release; editing an instruction file in a task does not change its authority.

Configure **Read-only reviewer reconsideration** separately from **Judge** in rollout settings. Each has its own API provider/model and human-approved input/output price ceilings per million tokens (`reconsiderationAgent` / `reconsiderationTokenPricing`, `judgeAgent` / `judgeTokenPricing`). Both support Claude or OpenAI APIs without repository tools. A CLI initial reviewer can submit its ordinary findings, then a configured read-only API reviewer reconsiders the appeal before the separate judge. The reconsideration model takes precedence over the initial reviewer. Without an explicit reconsideration model, compatibility reuse is limited to an initial API reviewer matching the judge's provider, model, and endpoint exactly; only then may it use that judge's price ceilings. Missing models or ceilings send an actionable request to the human docket. Clearing the reconsideration model and its ceilings removes that optional configuration. All calls reserve the same durable task-wide token, cost, and elapsed-time budgets before invoking either model.

## Dockets and durable holds

Standards findings cite rule revisions and concrete code evidence. Defects need no preexisting standard. Appeals include the requested exception, alternatives analyzed, evidence, risks, and limits. Reviewer reconsideration and judge calls have persistent task-wide budgets. Routine approvals and straightforward fixes do not need a judge.

The docket exposes require-fix, one-time allowance, reusable allowance with explicit path/rule/expiry predicates, request-evidence, and cancellation. Each decision records the named actor and rationale, code and policy binding, finding IDs, and immutable evidence. One-time allowances remain discoverable but do not authorize future exceptions. Revocation preserves the historical event while preventing future reuse and invalidating pending approval.

Waiting cases retain the worktree, release agent slots, and survive restart. Normal task reopening, notification deletion/resolution, and autonomy changes cannot clear a hold. Human allowances do not waive another angle's blocker, failing hard checks, or protected-path scope. Changed code requires renewed review. The final serialized candidate admission checks the durable state rather than trusting a notification's status.

Archiving or deleting a governed project requires the separate owner capability and completed governed work, with no outstanding docket or remote publication. The home-screen confirmation requests this capability only when needed and retains it in memory. Historical policy evidence stays retained independently of ordinary project cleanup.

Task scope is captured atomically when a task is created; later task wording cannot grant protected-path permission. Legacy tasks without creation-time provenance need an authorized scope decision before assignment or a new explicitly scoped task. Changes to policy sources, checker scripts/configuration, or authority code require a separate exact-code human approval in Standards. Dependency-only package changes do not require this approval. Source drift remains visible until an evaluated amendment reconciles the approved hashes.

Governed projects publish SPEC changes through an explicitly scoped Execute task with normal review and hard checks. Approval in the standalone specification-publication workflow cannot substitute for that authority.

Publication receipts preserve the reviewed files and their original scope before the local merge. A remote rebase may carry that approval forward only when trusted code verifies the files and authority remain valid. Conflict resolution or other changed code creates a retained review task against the actual remote base, with the original scope for each file. The task starts with independent review and hard checks; any subsequent fix must be reviewed again. A failed or waiting remote publication cannot trigger automatic deployment. Cancellation, expiry, and critical revocation also block closed local tasks whose remote publication is still pending.

Manual and automatic delivery share the publication lease and require a clean, verified deployable revision before external commands run. Deployment-command and environment settings require the owner capability in governed projects. Repository commands, checks, installers, and delivery subprocesses strip governance capabilities even when command-specific environment overrides try to restore them.

Critical policy revocation invalidates pending approvals, pauses affected agents/tasks, and preserves evidence. Activate a compatible evaluated replacement release, then request a fresh policy review from the stale docket. This explicit action preserves the original scope and spent budgets and grants no code approval. Already published commits remain unchanged and receive an explicit remediation marker. Ordinary release activation affects new assignments; critical revocation is a separate administrative action.

## Congress and amendments

Decision mining has its own durable cursor and runs independently of code-audit change detection. Recurrence nominates a rule for review; it does not justify changing it. A configured API auditor can draft exact substantive standard text from supporting and contrary decisions. Draft claims are durable and bounded; failed drafts stay available for manual follow-up. The UI also permits manually authored exact proposals. None of these paths activates a rule.

The cursor also processes retained fixes, reconsidered findings, verified dispositions, and reviewer false positives. Such events are labeled advisory evidence, separately from human rulings; they never acquire reusable authority. Distinct cases count toward recurrence, and exact processed-event receipts prevent late or same-time events from being skipped. Draft jobs have expiring claims, at most three attempts, and backoff; failed nominations do not starve later work.

Proposals show complete before/after content, supporting and contrary rulings, positive/negative examples, scope, compatibility, and a required landed enforcement commit. Evaluation binds the candidate content hash. Human activation uses optimistic concurrency against both the proposal and current release. Rollback restores a previously approved immutable release only with compatible enforcement. Unlanded or incompatible enforcement requires a normal scoped implementation task; unrelated Git commits are never reverted automatically.

## Offline replay executor

The old synthetic baseline/candidate outcomes are removed. Production replay uses a server-owned `OPENSPRINT_REPLAY_IMAGE` value pinned to an immutable Docker image digest, for example `registry.example/replay@sha256:<64 hex characters>`. There is no network pull: provision the image and its offline model/toolchain before evaluation. Missing Docker, image, original prompt/commit/fixture, unsupported dependencies, or an incomplete evaluator output produces **incomplete evaluation**, never successful evidence.

Docker is resolved from trusted absolute installation locations rather than the task's `PATH`. A custom installation can use the server-owned absolute `OPENSPRINT_REPLAY_DOCKER` path. A bounded archive reader validates every path before extracting; reserved Git metadata, duplicate/case-conflicting paths, links, and special files are unsupported. Fresh local Git state supports agent commits without exposing host remotes, credentials, hooks, or configuration.

The image must contain two executables:

1. `/opensprint-replay/agent /replay-input/task.json` invokes an actual offline coding agent against `/workspace`. The input contains the original decomposed task input, full selected baseline/candidate instructions, and toolchain identity. Honor `executionContract`, `contextDirectory`, and `resultPath`: resolve `context/` references under the supplied directory and write only the relocated result path. The original absolute worktree prefix is mapped to `/workspace`; local commits are permitted, merging/publishing and external effects are unavailable. Emit one JSON object on stdout: `{ "completed": true, "retryCount": 0, "costUsd": 0 }`. Cost must reflect measured execution; zero is appropriate for a local offline model with no API bill. Send logs to stderr.
2. `/opensprint-replay/evaluate /replay-evaluation/rubric.json` runs a fixed independent evaluator and every named deterministic check. Emit `{ "rubricId": "...", "label": "compliant", "reviewPassed": true, "checks": [{ "name": "unit", "passed": true }] }`. The evaluator and rubric must not be supplied or modified by the candidate. The five labels are `compliant`, `exception`, `defect`, `conflict`, and `retrieval_miss`.

The server exports tracked source from the retained original base commit into disposable directories. Untracked environment files, live task stores, Git credentials, connectors, and server capabilities are never mounted. Potentially sensitive tracked inputs are rejected. Containers use no network, a read-only image root, an unprivileged UID, dropped capabilities, no-new-privileges, resource/time limits, and a bounded temporary filesystem. Only the workspace is writable for the coder. The evaluator runs in a fresh container with a read-only candidate workspace and receives a rubric unavailable to the coder. Container names permit forced cleanup after client timeout. The model and required dependencies must already be in the image; downloading them during replay is unsupported.

Backends running as root assign the validated replay inputs to UID/GID 65534 before launching either container. Completed coder output is untrusted: links, special files, and oversized artifact trees make evaluation incomplete before host cleanup or diffing. If the Docker connection fails and forced container termination cannot be confirmed, its private temporary directory stays quarantined. Stop the corresponding `opensprint-replay-*` container before removing that directory.

Use the advanced replay section to label a retained completed task session. Before ordinary session pruning, the server retains the exact attempt/invocation, original policy pin, decomposed/full prompts, binary context/specification/plan/dependency artifacts, and original base/head/diff. Routine approvals can supply compliant examples without an appeal. Missing or ambiguous provenance, linked context, or retention-budget overflow makes replay unavailable. Rubrics, labels, and holdout flags are human-authored immutable inputs. Fixtures and full outcome artifacts, including binary code diffs, live under `~/.opensprint/governance-replay/`, outside ordinary session pruning; original inputs also have independent database records and Git retention refs. Treat this evidence as private project data and back it up with the policy database. Never invent missing original inputs. Candidate policy replaces the original policy projection while requirement/dependency evidence stays pinned.

Evaluation requires at least ten fixtures, all five categories, and held-out positive and negative examples. Every candidate example must pass its independent rubric: an aggregate tie cannot hide a known missed violation. It compares real measured task success, review outcomes, retries, latency and cost against baseline; regressions prevent activation. This minimum is an activation prerequisite, not evidence of broad improvement. Start with a human-measured baseline and sample routine approvals to detect violations that never escalated. Track human minutes, queue age, reversals, retrieval coverage, escaped regressions, and total cost/latency. Insufficient or conflicting evidence keeps rollout in shadow mode.

Completed sessions with non-failed live user guidance are unavailable as replay fixtures until the full model-turn protocol is supported. Their case evidence retains the exact guidance journal; replay never presents the original prompt alone as the complete input to a guided run.

API entry points are under `/api/v1/projects/:projectId/governance`. The `/replay/sources` and `/replay/fixtures` reads show available retained inputs; capability-protected fixture labeling and `/replay/proposals/:proposalId/evaluate` run the evaluator. No HTTP endpoint accepts arbitrary evaluation scores.
